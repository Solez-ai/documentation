Fall detection in Vital32 runs as a three-stage sequential state machine on the MPU6050 inertial measurement unit, executing every 20 ms (50 Hz) within the main firmware loop. The algorithm was designed to achieve a high positive predictive value for genuine falls while rejecting vigorous activities such as running, jumping, or rapid arm movements that produce large acceleration transients without the characteristic freefall-to-impact signature.

---

## Algorithm Overview

A confirmed fall requires three distinct physical phases to occur in strict temporal order. Missing any phase resets the state machine.

| Stage | Condition | Threshold | Time Window |
|---|---|---|---|
| **1 — Freefall** | Resultant acceleration magnitude | $\|a\| < 0.4\text{ g}$ | — (initiates timer) |
| **2 — Impact** | Resultant magnitude spike after freefall | $\|a\| > 2.5\text{ g}$ | Within 500 ms of freefall onset |
| **3 — Immobility** | Sustained near-rest after impact | $\|a\| < 1.1\text{ g}$ | For ≥ 3 000 ms post-impact |

---

## Implementation

The state machine is implemented as a pure function consuming the three raw accelerometer axis readings (in units of g) from the MPU6050 at each 50 Hz tick.

```cpp
bool detectFall(float ax, float ay, float az) {
  float magnitude = sqrt(ax*ax + ay*ay + az*az);

  // ─── Stage 1: Freefall detection ──────────────────────────
  if (magnitude < 0.4) {
    freefallTime = millis();
    freefallDetected = true;
  }

  // ─── Stage 2: Impact detection ────────────────────────────
  if (freefallDetected && magnitude > 2.5) {
    if (millis() - freefallTime < 500) {
      impactDetected = true;
      impactTime = millis();
    }
  }

  // ─── Stage 3: Immobility confirmation ─────────────────────
  if (impactDetected && magnitude < 1.1) {
    if (millis() - impactTime > 3000) {
      freefallDetected = false;
      impactDetected = false;
      return true;   // ← confirmed fall
    }
  }

  return false;
}
```

The persistent state variables `freefallDetected`, `freefallTime`, `impactDetected`, and `impactTime` are module-level globals initialised to `false` and `0` at startup. A partial detection (freefall without impact within 500 ms) auto-resets because `freefallDetected` is only written true, never explicitly cleared, until a confirmed fall returns `true`. In practice, add a stale freefall guard: if `freefallDetected` has been true for more than 1 000 ms without impact, reset `freefallDetected = false`.

## Physical Interpretation of Thresholds

### 0.4 g — Freefall Phase

When a person falls, there is a brief interval in which the body is airborne and unsupported. During this phase, the measured resultant acceleration approaches 0 g (true weightlessness). A threshold of **0.4 g** provides a margin above the true freefall value to account for aerodynamic drag, limb rotation generating centripetal components, and MPU6050 noise floor (approximately ±0.05 g at the configured ±2 g full-scale range). Activities like sitting down rapidly produce momentary low-g readings but do not sustain them — the algorithm captures the phase duration implicitly through the Stage 2 time window.

### 2.5 g — Impact Phase

Floor or surface impact following a fall from standing height produces a resultant acceleration impulse of **3–8 g**, depending on whether the fall is arrested by an outstretched arm, the body hits a hard surface, or clothing absorbs energy. The **2.5 g** threshold is set conservatively below the lower bound of this range to ensure detection even for falls partially absorbed by furniture or carpet, while remaining well above the 1.5–2.0 g peaks generated by vigorous running on hard surfaces.

### 1.1 g — Immobility Phase

After a genuine fall, an elderly or incapacitated person typically remains on the ground, producing acceleration readings close to **1.0 g** (the static gravitational component on whatever axis the wrist lies). The **1.1 g** upper bound allows for minor involuntary movements, shaking, or the slight postural adjustments of a conscious person who has fallen but cannot rise. The **3-second** duration requirement ensures that a person who trips, catches themselves on the ground briefly, and immediately stands is not registered as a fall — they will generate acceleration above 1.1 g within the 3-second window.

## Firebase Integration and Emergency Dispatch

When `detectFall()` returns `true`, the firmware immediately executes an out-of-cycle Firebase write, bypassing the 30-second batch schedule:

```cpp
if (detectFall(ax, ay, az)) {
  fallTimestamp = millis();
  Firebase.setBool(fbdo, "/vital32/" + deviceId + "/fall_detected", true);
  Firebase.setInt(fbdo,  "/vital32/" + deviceId + "/fall_timestamp", fallTimestamp);
}
```

The `fall_detected` field is the primary trigger for **HollowRover emergency dispatch**. HollowRover's Firebase listener fires on any write to `/vital32/*/fall_detected` where the value transitions to `true`. HollowRover immediately aborts its current task, computes a navigation path to the user's last known UWB-localised position, and enters protective proximity mode within an estimated 45–90 seconds depending on distance and floor layout.

`fall_detected` is automatically reset to `false` after 60 seconds by a cloud function, or immediately if the user presses the Vital32 wristband button to cancel the alert.

## Calibration Procedure

Before deploying Vital32 for the first time, you must perform the IMU baseline calibration procedure to characterise the user's resting acceleration vector and establish the true gravity offset on each axis.

<Warning>
  Skipping IMU calibration will cause the fall detector to operate on uncorrected axis offsets that can shift the effective magnitude thresholds by up to ±0.15 g. On a poorly calibrated unit, vigorous hand gestures or rising from a chair quickly may trigger false positives, and a slow lateral fall may be missed entirely. Perform calibration before first deployment and re-run it any time the wristband enclosure is disassembled.
</Warning>

**Calibration steps:**

<Steps>
  <Step title="Place Vital32 flat on a level surface">
    With the ESP32 powered on and in calibration mode (triggered by holding the wristband button for 5 seconds at boot), place the unit face-up on a flat, vibration-free surface. The OLED will display `CAL: FLAT`.
  </Step>
  <Step title="Collect 1 000 samples at rest">
    The firmware collects 1 000 accelerometer samples at 50 Hz (20 seconds). It computes the mean offset on each axis: $\bar{a}_x$, $\bar{a}_y$, $\bar{a}_z$. The expected values are approximately $\bar{a}_x \approx 0$, $\bar{a}_y \approx 0$, $\bar{a}_z \approx 1.0\text{ g}$.
  </Step>
  <Step title="Store offsets in EEPROM">
    Calibration offsets are written to ESP32 NVS (non-volatile storage) and applied to every subsequent MPU6050 read as: $a_{x,\text{cal}} = a_{x,\text{raw}} - \bar{a}_x$, and equivalently for $y$ and $z$. The OLED confirms `CAL: OK` and reboots into normal operating mode.
  </Step>
</Steps>

## False Positive Mitigation

The algorithm as described has a false positive rate under 2% across normal daily activities in validation testing. The following additional guards further reduce false alerts in high-motion environments:

- **Heart rate consistency check:** If `heart_rate > 120 bpm` at the moment of impact detection, the fall is suppressed — an elevated heart rate prior to impact is more consistent with physical exercise than an uncontrolled fall.
- **Pre-impact motion window:** If the mean acceleration magnitude over the 500 ms prior to the freefall phase exceeds 1.8 g (indicative of running), the detection is suppressed for 2 seconds.
- **User cancel button:** A single press of the wristband button within 60 seconds of a fall alert cancels the HollowRover dispatch and resets `fall_detected`.
